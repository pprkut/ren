# 0007 — Sync engine (M3)

**Status:** done (2026-10-07), for review; measured against the real
server.

## Context

`docs/PLAN.md` describes the sync: push the queue of local changes, then
replace folders and feeds, then fetch the items — all unread and starred
ones the first time, the changes since a cursor (`/items/updated`) later,
with a paged resync if that fails. M3 builds it as the `ren-sync` crate,
on top of the client (M1, `0003`) and the store (M2, `0006`), as a
function the app runs on a background thread.

## What was built

**`ren-sync`:** `sync(api, store, clock, options, progress)` runs one sync
synchronously and returns a `Report` (kind, items, new items, corrected
states, purged items, changes sent or refused).

- `NewsApi` is what the sync needs from the server: folders, feeds, one
  page of items and the changes (both handed over item by item), write
  requests, and the server's clock. `Client` implements it; the tests use
  an in-memory fake server. `Clock` is the local time (purge ages, the
  time since the last sync).
- **Push:** the queued "mark all as read" requests first, then the read,
  unread, star and unstar changes in batches of at most 1,000 ids. An
  entry leaves the queue only after a 2xx. A request the server refuses
  (an HTTP error status) stays queued and is reported, and the sync goes
  on; no connection or a 401 stops it.
- **Folders and feeds** are replaced as a whole (`replace_folders`,
  `replace_feeds`; removed feeds take their items).
- **Items:**
  - The **initial sync** pages through the unread items, then the
    starred ones, 1,000 per request.
  - An **incremental sync** clears the "new" marker, fetches the changes
    since the cursor and moves the cursor to their newest `lastModified`.
  - A **resync** pages through the unread and starred items like the
    initial sync, and corrects the state of the local items that are no
    longer in these lists. It replaces the incremental sync when fetching
    the changes fails (anything but a 401, e.g. the HTTP 500 a too large
    response gets, see `0003`), or when the last sync is 30 days or more
    ago.
  - Items are written in **chunks of 200**, one transaction each, while
    the response is received; neither a page nor `/items/updated` is ever
    held in memory as a whole.
  - A full sync (initial or resync) **stores its progress** after each
    page and resumes with the page that failed, also after a restart.
- **Purge:** read, unstarred items unchanged for 30 days (M8 makes it a
  setting; `None` keeps them).
- **Progress:** the callback gets "pushed", "feeds stored" and the number
  of items stored after each chunk, with the expected total in a full
  sync (the feeds' unread counts plus the starred count), so M5 can show
  the list filling up during the initial sync. Returning `Break` cancels
  the sync after the current chunk; what was stored stays, and a full
  sync resumes next time.

**`ren-store`** (schema version 2):

- `mark_all_read(scope, newest_item_id)` for everything, a folder, the
  feeds outside of folders or a feed, queued as one request in
  `pending_mark_read` instead of one id per item. It drops the queued
  read states of the items it covers; until it is sent, those items stay
  read whatever the server sends.
- `reconcile(state, ids, listed)` for the resync (below).
- `sync_value`, `set_sync_values`: numbers the sync keeps between runs
  (the progress of a full sync, the time of the last sync).

**`nextcloud-news`:** `Client::server_time`, the `Date` of the latest
response (`httpdate`, already in the lock file through Servo).

**`ren --sync <DB> [--resync]`** syncs into a database outside the source
tree and prints time, CPU, requests and memory; `just measure-sync` runs
the four steps below against the real server.

### Choices and findings

- **The cursor after a full sync is the server's time when the sync
  started** (the `Date` of the feeds request, a minute earlier for a
  proxy's clock; the local clock if there is none), not the newest
  `lastModified` of the listed items. A full sync takes minutes on a large
  account and the items change meanwhile; with the server's start time,
  the next sync fetches those changes. The newest `lastModified` can also
  be far in the past: after "mark all as read" on the web, no item is
  unread, the cursor would stay at the newest starred item, and every
  later `/items/updated` would return the whole mass change again — the
  response that fails on a large account, so every sync would end in a
  resync.
- **Resync, page by page.** The lists of unread and starred items don't
  say which items stopped being unread or starred. Each page covers the
  ids from its lowest one up to where it started (the last page down to
  0), so after each page the local items in that range that are unread
  (starred) but weren't listed are marked read (unstarred), except those
  with a pending change. Only one page of ids is held, and the resync can
  be resumed like the initial sync. Items that change on the server while
  the resync runs are fetched by the next sync (the cursor rule above).
- **"Mark all as read" is queued as such.** One request instead of up to
  63,000 ids (63 requests the server works through item by item). Its
  ordering against single changes: it drops the queued read states it
  covers, so whatever is queued for an item afterwards is newer, and the
  push sends it first. If the server refuses it, the read changes of
  single items are held back too, since it would undo them when it goes
  through later. The feeds outside of folders are marked feed by feed
  (folder 0 fails, `0003`); a 404 (the feed or folder was deleted on the
  server) drops the request, as there is nothing left to mark.
- **A refused change doesn't stop syncing.** One change the server keeps
  refusing would otherwise block every later sync. It stays queued,
  is reported (M5 can show it) and is tried again by the next sync. No
  connection, a 401 or a database error stop the sync instead: the
  following requests would fail too.
- **When the "new" marker is cleared:** when an incremental sync or a
  resync starts on the items, after the push and the feeds succeeded, so
  a sync that fails early (offline) doesn't take the marker away. A
  resumed full sync keeps the markers of its first part.
- **Chunks of 200.** Measured with 50, 200 and 1,000 (below): 1,000 adds
  about 2.5 MiB to the peak, 50 saves about 0.2 MiB over 200 but costs a
  quarter more CPU (more transactions). A chunk of 200 takes about 7 ms
  to write (35 ms per 1,000 in `0006`), which is how long a UI write can
  wait for the sync's.
- **The fake server** (`src/fake.rs`) keeps folders, feeds and items in
  memory, answers like the News app (paging by id, `getRead`, the
  changes by `lastModified`, unknown ids skipped, 404 for unknown feeds
  and folders, HTTP 500 for folder 0), logs the requests and fails them
  on request, also mid-response. The integration test runs the real
  client against nextcloud-news's mock HTTP server with the recorded
  fixtures.

## Measurements

In the cloud container (4 vCPUs, Xeon at 2.8 GHz, shared), against a
synthetic News server on localhost (a Python script, outside the
repository: plain HTTP, no gzip, 61,803 unread items of 49 feeds with
bodies of about 0.7–5 KiB, most of the time spent in the script building
responses). `ren --sync` from a release build without Blitz and Servo,
at 11adaa8. These show what the sync itself costs, not the real server:

| step | kind | requests | items | wall s | CPU s | RSS before MiB | peak RSS MiB | RSS after MiB | after malloc_trim MiB | database MiB |
|---|---|---|---|---|---|---|---|---|---|---|
| initial | initial | 65 | 61803 | 15.1 | 2.56 | 7.3 | 13.4 | 13.4 | 12.9 | 229.0 |
| incremental (no changes) | incremental | 3 | 0 | 0.1 | 0.01 | 7.1 | 12.2 | 12.2 | 12.2 | 224.2 |
| resync | resync | 65 | 61803 | 13.0 | 2.01 | 7.1 | 13.2 | 13.2 | 12.7 | 228.7 |

- **Memory is flat over the sync.** RSS while syncing (sampled after each
  chunk): 7.1 MiB at the start, 9.4 MiB with the database open (SQLite's
  code and schema), 9.9 MiB after the feeds, 11.8 MiB after the first
  chunk (SQLite's page cache filling, the response buffers), then
  13.4 MiB from the first thousand items to the last of 61,803.
- **RSS doesn't drop after the sync, but it isn't the sync's data:** an
  incremental sync with no items at all ends at 12.2 MiB, 1.2 MiB below
  the initial sync's. `malloc_trim` gives 0.5 MiB back (0.0 after an
  incremental sync) at chunks of 200, 2.4 MiB at chunks of 1,000. (On
  the real server it gives back 2.2 MiB after a resync, see below.)
- **Chunk sizes**, initial sync, two runs each:

  | chunk | peak RSS MiB | after malloc_trim MiB | CPU s (user + sys) |
  |---|---|---|---|
  | 50 | 12.7–12.9 | 12.6–12.8 | 3.16–3.25 |
  | 200 | 13.0–13.4 | 12.5–12.9 | 2.56–2.64 |
  | 1000 | 15.4–15.9 | 12.9–13.3 | 2.39–2.41 |

- **Writing is cheap next to the server:** 2.6 s of CPU for 61,803 items
  including decoding (M1: 1.2 s for decoding alone, M2: 1.5 s for
  writing alone). The real server takes about 2 minutes for the initial
  sync of the same size (`0003`).
- The store's write speed is unchanged by the "mark all as read" check
  in the upsert: `just measure-store`, three runs each of master and this
  branch, interleaved: initial 2.53–2.79 s (master) and 2.64–2.67 s, an
  incremental sync of 1,200 items 105–111 ms and 113–129 ms.

### Against the real server

`just measure-sync` at c8220a9 by the user (i7-1185G7, Linux 7.2.8;
News 28.7.0, 11 folders, 49 feeds, 63,227 unread and 20 starred items;
release build with the default features, one run per step, into a new
database):

| step | kind | requests | items | added | wall s | CPU s (user + sys) | RSS before MiB | peak RSS MiB | RSS after MiB | after malloc_trim MiB | database MiB |
|---|---|---|---|---|---|---|---|---|---|---|---|
| initial | initial | 67 | 63247 | 63247 | 123.292 | 1.91 | 10.3 | 20.0 | 18.7 | 18.0 | 226.8 |
| incremental | incremental | 3 | 0 | 0 | 4.603 | 0.01 | 10.3 | 18.2 | 18.2 | 18.2 | 221.2 |
| resync | resync | 67 | 63247 | 0 | 122.815 | 1.69 | 10.2 | 20.7 | 20.7 | 18.5 | 225.3 |
| incremental again | incremental | 3 | 0 | 0 | 4.610 | 0.01 | 9.9 | 17.9 | 17.9 | 17.9 | 221.2 |

- **The server sets the pace:** the initial sync of 63,247 items takes
  2 minutes, as long as fetching alone (116 s at a batch size of 1,000
  in `0003`); storing the items costs 1.9 s of CPU, 1.5 % of the wall
  time. A resync takes as long as the initial sync.
- **An incremental sync takes 4.6 s for three requests and no items:**
  the server's fixed cost of about 1.5 s per request (`0003`). Fine for a
  timer every 15 minutes; a manual refresh will feel it. Right after a
  full sync, `/items/updated` returned nothing: the minute of margin on
  the cursor costs nothing in practice.
- **Memory:** 20–21 MiB at the peak, 10 MiB above the start. Most of it
  is the fixed cost of syncing at all: a sync without items ends at
  18 MiB too (TLS and the system's certificates, gzip, the open
  database; about 5 MiB with plain HTTP in the container). The initial
  sync leaves 0.5 MiB more than that, the resync 2.5 MiB, of which
  `malloc_trim` gives back 2.2 MiB. Next to fetching alone (M1: peak
  14.9 MiB from 10.1 MiB), the store adds about 5 MiB, the same for
  every sync size.
- **`malloc_trim` after a full sync** (initial or resync) is worth it
  for M5: up to 2.2 MiB back for a call that costs nothing. After an
  incremental sync it gives nothing back.

## Open

- **An incremental sync costs 4.6 s on the real server,** almost all
  in the server's fixed cost per request. Fetching folders and feeds
  less often than the items would save two of the three requests; M8
  can decide with the periodic sync.
- **`malloc_trim` after a full sync** goes into M5's sync thread (glibc
  only).
- **Batches of 1,000 ids** are still not verified against a server. A
  batch the server refuses stays queued, and is tried again by every
  sync, holding back the rest of its kind; if that happens in real use,
  split refused batches (halving down to single ids would also find a
  single id the server can't take).
- **Threading and scheduling** are M5's and M8's: run `sync` on a
  background thread at a lower priority (`nice`), on a timer and on
  request, never twice at once; open the store a second time for it.
- **The purge** scans all items every sync (about 0.2 s at 63,000 items,
  `0006`); once a day would do. Its age and `resync_after` become
  settings in M8. Items a resync marks read keep their old
  `lastModified` (the server's isn't sent for items that aren't
  listed), so the purge can delete them right away if it is old.
- **"Mark all as read" for the starred list** has no request on the
  server; the UI can mark the listed items one by one if it offers it.
- The fake server is private to `ren-sync`'s tests. If M5's view-model
  tests want to drive a sync, it becomes a `testing` feature.
