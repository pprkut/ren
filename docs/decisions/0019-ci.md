# 0019 — CI's workflows and checks

**Status:** done (2026-10-19; Codecov 2026-10-22); performance tracking
planned (2026-10-25).

## Context

CI was one workflow, `ci.yml`, for every push and pull request: the
heavy jobs (Blitz, Servo's helper, the end-to-end test) skipped
themselves on pushes to branches, a branch with a pull request ran the
light checks twice, and the commands were written out twice, in the
workflow and in the `justfile`. Its actions were pinned by tag; the
build caches, about 3.5 GiB per commit of `master` and as much again per
pull request, outgrew the repository's 10 GiB, so pull requests pushed
out `master`'s. Some checks were promised but not run: `rust-version`
(1.92), the validation of the `.desktop` file and the AppStream
metadata (0018), the dependencies' security advisories. lintpkg's CI,
split into workflows and with a few more checks, was the model.

## Workflows

Split by when they run (the plan's "Conventions" lists what each runs):

- `general.yml`, on every push: checks of the files that need no build.
- `dependencies.yml`, on every push and weekly: cargo-deny and the
  notices. Weekly, because advisories come without a commit.
- `code-tests.yml`, on every push and weekly: without the engines.
  Weekly, for the new stable toolchain's lints.
- `full-tests.yml`, for pull requests, `master`, weekly and on demand:
  the engines, the oldest Rust, the end-to-end test.

Their triggers replace the heavy jobs' conditions. The light checks run
on pushes only, so a pull request from a fork gets only the full tests;
for a repository without outside contributions that's acceptable.
Scheduled runs skip themselves in forks.

Each job runs a `justfile` recipe; `check`, `check-light` and
`check-servo` are lists of the same recipes, so CI and the local checks
can't drift apart. Rust jobs set up with `.github/actions/setup-rust`
(the system libraries, the toolchain with the runners' rustup, the
cache, the tools from taiki-e/install-action, just among them), used by
GitHub's self-repository syntax (`uses: $/...`): it's taken from the
workflow's commit, not the checkout, and counts as pinned.
dtolnay/rust-toolchain is gone: it has no releases, dependabot couldn't
update its pin. `extractions/setup-just` was the alternative for just;
install-action was already used and checks its downloads' checksums.

Caches are saved on `master` only; branches and pull requests restore
`master`'s. A cache key changed with the setup action (rustup doesn't
set `CARGO_HOME`, which rust-cache hashes), so the first runs after it
built without one.

## Hardening

Actions are pinned by commit, with the release as comment, and updated
by dependabot weekly, after a week's cooldown (the workflows and the
composite action). Not Cargo: Servo and Blitz pin many crates and their
stylo versions have to stay apart, updates are done by hand. Checkouts
don't keep the token, the workflows grant no permissions and each job
asks for `contents: read`, a new push to a branch cancels its running
checks (not on `master`). zizmor checks all of it; its findings are in
the job's log, not GitHub's code scanning, as in lintpkg.

## Checks

What each found when it was added, and what was decided:

- **`.desktop` file and AppStream** (`desktop-file-validate`,
  `appstreamcli validate --pedantic`): nothing.
- **zizmor:** the setup action by `./` instead of `$/`.
- **MSRV:** both workspaces with their `rust-version`, read from their
  `Cargo.toml`, and the default features, as packages build them: Blitz
  and Servo build with 1.92. `cargo check` only, in about 4 minutes.
- **Advisories** (`cargo deny check advisories`): four vulnerabilities in
  rustls 0.23.45 (RUSTSEC-2026-0346 to -0349), which ren uses as the
  client they are about, so both workspaces went to 0.23.46; a yanked
  yoke-derive 0.8.3. Unmaintained crates count for the workspaces' own
  dependencies only (`unmaintained = "workspace"`): the 4 in ren's tree
  (ttf-parser, zbus's sub-crates) and 6 in the helper's (bincode, unic-*)
  are Slint's, zbus's and Servo's, with nothing to update to. Yanked
  crates fail instead of only warning.
- **cargo-machete:** one false positive, wayland-backend, a dependency
  only for its `client_system` feature; ignored in `crates/ren/Cargo.toml`.
- **typos:** 18 findings, none a typo: "PNGs", the generated notices,
  the fixtures' feed data, and the settings tests' misspellings on
  purpose. These are ignored only with the words around them
  (`extend-ignore-re`), so the same typo elsewhere is still found.
- **EditorConfig:** the new `.editorconfig` has what the files did
  already. editorconfig-checker doesn't check the indentation's width
  (`.editorconfig-checker.json`): its 88 findings were continued string
  literals and aligned arguments, and rustfmt checks Rust's.
- **shellcheck** (0.11.0, pinned: the runners' may be older): an unused
  variable and a parsed `ls` in `measure-page-loads.sh`.

## Codecov

The full job's coverage (LCOV) and test results (JUnit) go to Codecov,
as lintpkg's do: uploaded by OIDC from a job of its own, so the right to
an OIDC token never meets the job that builds and runs the crates' code;
pull requests from forks upload without a token. The results are
uploaded also of failed tests, the coverage only of a passing job. A
failed upload doesn't fail the run, and `codecov.yml` makes Codecov's
checks informational: no coverage threshold fails CI (0015).

For the JUnit results the full job's tests run under cargo-nextest
(`cargo llvm-cov nextest`, the `ci` profile in `.config/nextest.toml`),
each test in a process of its own; locally `cargo test` stays the
runner. nextest doesn't run doc-tests, but neither did cargo-llvm-cov,
and the one there is runs in `code-tests.yml`. First upload: 378 tests,
84 files, 78.91 % of 18,656 lines (Codecov's count; the job's summary
says 78.10 %). The full job takes 2 minutes.

The numbers include test code: cargo-llvm-cov leaves out `tests/`, but
not the test-only files (`testing.rs`, `ui/flows.rs`, 453 lines) nor
the inline `#[cfg(test)]` modules (5,776 lines in 72 files), covered at
nearly 100 %. Without them the first upload is at 68.6 % of 12,427
lines. Leaving them out takes `#[coverage(off)]` on each test module,
unstable in Rust 1.99 (nightly only), or the tests in files of their
own (`foo/tests.rs`, as Rust's standard library does), excluded by name:
a nightly toolchain and a second Blitz build in the full job, or 72
files' tests moved. Neither is worth it for now; the percentage is a
trend, and the test code stays in it until the attribute is stable.

## Performance tracking

*Planned (2026-10-25).* The measurements so far are run by hand
(`scripts/measure*.sh`, `just measure-all`) and their numbers end up in
decision records; nothing notices when a change makes ren bigger or
slower. The steady ones should run in CI for every pull request, with
their history kept and regressions reported on the pull request.

### Choosing a service

- **CodSpeed:** free for open source, and its CPU simulation (instruction
  counts under Valgrind) gives steady numbers on shared runners, but it
  only takes benchmarks written with criterion or divan. That would fit
  ren-store and the sync path, not what ren's goals are about: the
  window's memory, idle CPU, frames, the tabs. Its memory instrument
  counts only the benchmarked function's heap.
- **github-action-benchmark:** takes any numbers (`customSmallerIsBetter`),
  keeps them in a `gh-pages` branch with charts and no outside service,
  but compares only by ratio against the last run, and results from the
  desktop would have to be pushed to the branch by hand.
- **Bencher (chosen):** takes any numbers as Bencher Metric Format
  (BMF) JSON, keeps a history per machine ("testbed"), compares with
  statistical thresholds and comments on pull requests; results can be
  uploaded from anywhere with `bencher run`, so the desktop's runs get
  their own testbed. Free for public projects (65,535 metrics a day);
  the free plan's limits (one job at a time, 5 minutes) are for
  Bencher's own bare-metal runners, which ren doesn't use. Self-hostable
  under the Bencher License if the cloud's terms change.

Servo uses Bencher the same way: its measurements (binary sizes,
Speedometer, Dromaeo) write BMF, `etc/ci/bencher.py` merges them, and one
`bencher run --adapter json` uploads them; timings run on its own
machines, sizes on GitHub's runners, each as a testbed of its own.

### What is measured where

GitHub's runners are shared: time, CPU and frames vary from run to run,
memory under Xvfb with the software renderer doesn't (0016's runs agree
within 0.1 MiB at most stages). In CI:

- the window's anonymous memory and RSS at each stage of
  `measure-hidden` (with a synthetic dump) and `measure-settings`;
- the tabs' memory with `pattern-helper`, the stand-in for Servo's
  helper (0016), so the job doesn't build Servo;
- `measure-store`: the database's size and the list queries' memory;
  its timings with wide thresholds, if they turn out steady enough;
- the size of ren's release binary, stripped and unstripped (exact on
  any runner; Servo tracks its own the same way). The helper's once CI
  builds it in release.

Time, CPU and frames come from `just measure-all` on the desktop,
uploaded as the desktop's testbed.

### Pull requests from forks

Outside contributions are rare but welcome, and their pull requests
should be measured as well. A workflow run by `pull_request` from a fork
gets no secrets, so it can't upload. Servo uses `pull_request_target`
behind a label only maintainers set; running a fork's code with the
base repository's secrets is the "pwn request" hole, and the label is a
manual step. Instead, as Bencher recommends:

1. `performance.yml` (`pull_request` and pushes to `master`, no
   secrets) builds, measures and keeps the BMF JSON and the event's
   payload as an artifact. A fork's code runs only here, as in the
   tests.
2. `performance-upload.yml` (`workflow_run`, after a successful run of
   the first) runs from `master`'s copy of the workflow with the Bencher
   token and `pull-requests: write`. It checks out nothing and runs only
   `bencher run --adapter json` on the downloaded file, which reports
   on the pull request.

The artifact comes from the pull request, so it is data, not trusted:

- The pull request's branch in Bencher is `pr-<number>`, not the head
  branch's name (Bencher's example), which may be a fork's `master`.
- The number must be an integer, and the pull request's head commit
  (from GitHub's API) must be `github.event.workflow_run.head_sha`,
  which GitHub sets; the base commit for `--start-point-hash` comes from
  the same answer. `master`'s history comes only from pushes to it.
- Untrusted values reach commands through environment variables only.
- A closed pull request's branch is archived (`bencher archive`) by a
  `pull_request_target` workflow that only uses the number and checks
  out nothing.
- GitHub's approval for first-time contributors stays on.

Our own pull requests and pushes to `master` take the same path, so
every run tests the one forks use. `workflow_run` only fires for a
workflow already on the default branch: the upload can't be tried on
the branch that adds it.

Pull requests are compared with `master` (`--start-point`,
`--start-point-clone-thresholds`, `--start-point-reset`). Until the
thresholds have settled on real data, alerts don't fail CI.

## Results

Runs on the last commit of the checks' pull request: `general.yml`'s
jobs under 20 s each, `dependencies.yml` 6 s (cargo-machete) to 3 minutes
(the notices), `code-tests.yml` 2.5 minutes, `full-tests.yml` 1–4
minutes per job.
