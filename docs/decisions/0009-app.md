# 0009 — The window on the store and the sync (M5)

**Status:** done (2026-10-07), for review; the measurements with the
real server are still to be run (`just measure-window-sync`,
`DATABASE=… just measure`).

## Context

Until M4 the window of S1/S1b showed dummy data, or the items of a
`--dump-items` directory, through view models that sorted and filtered
in memory. The store (M2, `0006`), the sync engine (M3, `0007`) and the
settings with the app password (M4, `0008`) existed only for the command
line. M5 puts the window on top of them: the feed tree with unread
counts, the item list, the article pane, mark read on open, starring,
manual refresh with its status, and the sync on a background thread.

## What was built

- **The database** is `$XDG_DATA_HOME/ren/ren.db` (`ren-settings`'
  `paths::database`), or the one given with `--database`. It also holds
  the changes not yet sent, so it isn't a cache.
- **`reader.rs`**, the window's view model in plain Rust: the store, the
  feed tree, the item list and the item shown. Every change goes to the
  store first (and is queued there for the server); each operation says
  what the window has to update (`Changes`: counts, rows, the whole
  list). Tested on a store in memory, without Slint.
- **The feed tree** (`feed_tree.rs`) is built from the store's folders and
  feeds (ordered by name and title there), with the store's unread counts
  per feed. "Starred" is the first child of "All items", with the number
  of starred items. A feed without a title shows its URL. After a sync,
  the tree is built again with the collapsed folders kept; a selected
  feed or folder that is gone falls back to "All items".
- **Tree rows are updated in place** (`changed_rows`): when the rows show
  the same nodes, only the rows whose content changed are set in the
  Slint model; the model is replaced only when rows come or go (the
  S1b open issue from `0002`).
- **The item list** (`item_list.rs`) keeps the ids of the list in order
  and the Slint model fetches each visible row by id when the list view
  asks for it (the choice left open in `0006`). The store sorts and
  searches; the list only knows the query and the order.
- **Opening an item** marks it read. Items can be marked read or unread
  and starred or unstarred from their context menu and the Article menu
  (which says "Star" or "Remove Star" for the item shown). An item
  unstarred in the "Starred" list stays there until the list is selected
  again, so rows don't move under the pointer.
- **Mark as read** queues one "mark all as read" for a feed, a folder or
  everything, up to the newest item stored, so items that arrive
  meanwhile stay unread; nothing is queued if nothing is unread. The
  server has no such request for the starred items, which are marked one
  by one (`0007`).
- **Next unread** looks at the rows after the current one in chunks of
  100, so it doesn't load the whole list.
- **Filtered items** are hidden by the store's queries and counts (M2).
- **Demo data:** `--items N` and `--dump DIR` write generated items or a
  dump into a temporary database (removed at the end, never synced), so
  the measurement scripts work unchanged. `dummy.rs` and `dump.rs` are
  gone; the plain-text body variant of the article went with the dummy
  data.

### The sync thread

`sync_thread.rs`. "Fetch Feed" and "Fetch All Feeds" (F5, Ctrl+L, the
tool bar, the feed tree's menu) start a sync; the server fetches the
feeds itself, so both sync everything.

- **A thread per sync**, never two at once. Everything it opens, the HTTP
  agent, its own connection to the database and the Secret Service's
  D-Bus connection, ends with the thread. Nothing stays between syncs but
  the app password, which the window keeps (with the account it is for)
  so that the Secret Service or `password-command` is asked once per
  run; after a 401 it is asked again.
- **The app password is fetched on the sync thread**, never on the UI
  thread: the Secret Service blocks, also while the keyring asks to be
  unlocked (`0008`).
- **Lower priority:** the thread calls `nice(10)`, which on Linux changes
  only the calling thread. Not idle priority, so a sync still finishes
  on a busy machine.
- **`malloc_trim` after a full sync** (initial or resync), after the
  store and the client are dropped (`0007`).
- **A database belongs to one account.** The first sync records a hash
  (FNV-1a, stable across Rust versions) of `user@server`; a database of
  another account is refused ("move it away to start anew"), so that
  queued changes never reach the wrong server, where the item ids mean
  other items. Databases from `ren --sync` without the mark are claimed
  by the first sync.
- **Reporting:** events go through a channel, and the UI is woken with
  `slint::invoke_from_event_loop` to read them, the pattern of the
  article and page wake-ups. The status bar shows the progress ("Syncing:
  1200 of about 63000 articles") and the result, including changes the
  server refused (kept for the next sync) and a resync that replaced the
  changes after a failure; failures stay until the next message.
- **Cancel:** "Cancel Feed Fetches" is enabled while a sync runs and
  stops it after the current chunk; closing the window does the same.
  What was stored stays; a full sync resumes next time (`0007`).
- **The list fills up during a full sync:** while items arrive, the tree,
  the counts and the list are read again at most every 2 s (`0003`,
  `0007`). An incremental sync reads them once at the end.

### Settings

The settings file is read at start, and again (if its stamp changed,
`0008`) when the window becomes active and before every sync. Slint has
no window activation callback; the focus scope that has the focus gets
`focus-gained` with the reason `window-activation`, and the feed tree,
the item table, the article and the page forward it. The window forwards
the focus to the feed tree at start. Problems of the file go to the
status bar (the first) and stderr (all); the last good settings stay in
effect. The sync takes the account and `sync.keep-read-days` (the purge)
from them.

### Choices and findings

- **The ids of the whole list, not pages** (`0006`): sorting once and
  fetching the visible rows by id makes scrolling free in any order; the
  list costs 8 bytes per item. Reading the list again after a sync is
  one `item_ids` query (measured below).
- **Counts are queried again after each change**, instead of being
  adjusted in the tree: the unread count query runs on a partial index
  and stays cheap, and it can't drift from the store.
- **A thread per sync instead of a long-lived one:** M8's periodic sync
  can start the same thread from a timer; between syncs nothing is
  resident.
- **The sync status is a status bar message**, not a widget of its own;
  the cancel button shows that a sync runs.
- **Focus-based reloading misses** when the search field has the focus
  (Slint's `LineEdit` doesn't expose `focus-gained`); the reload before
  every sync covers what matters.

## Testing

- `reader.rs`: the initial lists and counts, selecting each kind of
  node, opening (marks read once, the article's fields), read and unread
  (queued), starring in and outside of the starred list, mark as read
  for a feed, a folder, everything and the starred items (and nothing
  queued when nothing is unread), next unread (also beyond a chunk),
  sorting and searching with the current item, and reloading after a
  sync that removed a feed and added a folder and items.
- `feed_tree.rs`: rows, branch lines and navigation with "Starred",
  collapsed folders kept, counts, `contains`, rows changed in place.
- `item_list.rs`: sorting by each column and searching through the
  store, rows and ids.
- `demo.rs`: generated items (ids, "new" and unread shares, bodies, the
  file removed) and dumps (unknown feeds skipped, duplicates, the limit).
- `sync_thread.rs`: the account claim, the hash, progress and result
  texts (refused changes, cancel, 401).
- By hand, in the container under Xvfb against a small mock of the News
  API (`http://127.0.0.1`): the first sync filling the list, an item
  opened and read, the read state pushed (`POST items/read/multiple`)
  by the next, incremental sync, cancelling, and a sync without an app
  password (no Secret Service) failing with the message in the status
  bar.

## Measurements

In the cloud container (4 shared vCPUs, Xeon at 2.1 GHz), not on the
user's machine and not against the real server: release build at
d54bdcb without the rendering engines, the software renderer on Xvfb,
and a mock of the News API on localhost (a Python script, not in the
repository) with 62,700 unread and 1,900 starred items with bodies of
2.4 KiB, like the account in S2, answering each page after 0.1 s. Two
runs of `ren --measure-sync`, which `just measure-window-sync` runs
against the real server:

| | run 1 | run 2 |
|---|---|---|
| RSS before the syncs | 25.7 MiB | 25.9 MiB |
| full sync: time, CPU (user + system) | 11.9 s, 2.2 + 0.8 s | 11.7 s, 2.1 + 0.9 s |
| RSS after it | 31.6 MiB | 32.1 MiB |
| incremental sync: time, CPU | 0.1 s, 0.07 s | 0.1 s, 0.06 s |
| RSS after it, and idle | 33.7 MiB | 34.1 MiB |
| peak RSS | 34.3 MiB | 34.9 MiB |
| lists read again during the full sync | 13–42 ms, once 144 ms | 18–82 ms |

- The time is the mock's; the real server took about 2 minutes for this
  account (`0007`). The CPU time is the whole process: the sync thread
  (1.9 s for a sync without the window in `0007`) plus the window
  reading the lists again and drawing them.
- **Reading the lists again** (tree, counts and the 63,000 ids) grows
  with the list to 35–42 ms, up to 144 ms once while the sync thread
  wrote. Every 2 s during a full sync this is at most a few percent of
  the UI thread; the window stays usable. If it shows on slower
  machines, the interval can grow with the list, or only the counts can
  be read during the sync.
- **Memory** stays well below the goal: 6 MiB more after the full sync
  (the sync thread's heap is trimmed, its database connection closed),
  2 MiB more after the incremental one. Not investigated; likely the
  page cache of the window's database connection filling up (SQLite's
  default is 2 MiB per connection) as the lists are read.

The idle window, 6 s after start, three runs each:

| data | RSS (anon) | event loop running after |
|---|---|---|
| the 64,500 synced items | 29.4–29.8 MiB (5.5 MiB) | 58–63 ms |
| 10,000 generated items (`--items`) | 29.3–29.7 MiB (5.5 MiB) | 33–40 ms, after 250–300 ms writing them |

The store adds nothing measurable to the idle window: only the visible
rows exist, and the list's ids are 0.5 MiB at 63,000 items. Starting
with the large database costs about 20 ms more (opening it, the counts
and all ids).

## Open

- **Measurements against the real server and on the desktop:**
  `just measure-window-sync` (a full and an incremental sync in the
  window into a new database: time, CPU, RSS, the cost of reading the
  lists again) and `DATABASE=~/.local/share/ren/ren.db just measure
  software` (startup, idle and scrolling with the real database instead
  of generated items). They also show whether the Secret Service's
  connection is gone after the sync (`0008`).
- **No sync at start and no periodic sync** yet: M8, with
  `sync.interval-minutes`. A new database shows a hint to fetch.
- **Changing the account** in the settings file makes the sync refuse
  the database; M8b's log out has to remove it (or keep one database per
  account).
- **Dates are shown in UTC** (as in S1); local time needs the time zone
  (`localtime_r`, or a crate).
- **Not implemented yet** (status bar message): adding, editing,
  renaming and deleting feeds and folders, import/export, opening a
  feed's homepage, "Copy Link Address" in the item menu (Slint has no
  clipboard API; the HTML view's clipboard comes with M6).
- From `0002`, still open: select the row on right click before showing
  its context menu.
